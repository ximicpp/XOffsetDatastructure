# 性能瓶颈与下一轮研究参考

日期：2026-10-22。源码参照：`next_cpp26` 的
`30bb5ca2487c88bb65ce0bab548b4c1d1d6fe563`（0.3.0-beta.1 开发线）。

本文从 R4.1 计划中抽取分析、机制假设和实验原则，供后续开发引用。
本次没有执行新的构建或性能测量；本文不是新的性能验收报告，也不是已冻结的实验协议。
PR 状态和数字是上述日期的快照，实施前应重新核对源码身份和实际前提。

## 1. 结论与证据边界

核心方向：以完整业务循环的成本为目标，先验证现有 V2 优化，再用独立原型探索
表示方式与生命周期的上限。速度、空间、正确性和能力差异一起决定采用范围。

- 优先研究加载/重载与高频修改；查询成本也较高，但缺少最新剖析。
- V1 的块头、TLS owner 热路径和重载后线性扫描已经在 V2 中解决，不能继续用旧剖析
  将它们列为当前瓶颈。见 [V2 格式与分配器](../../V2_FORMAT.md)。
- 第三轮正式结果来自 Apple M4、一个固定 demo 和特定适配器：10/12 是 V2 晋升时
  的成绩，不代表最新 beta 已重测。后续安全加固、重载复用等改变需要当前基线。
- 正式对比保留各库原生用法，例如 FlatBuffers Object API。它没有证明所有竞品具有
  相同的不可信输入保护；不能将速度比较解释为安全能力完全相同。
- 本文区分历史正式结果、PR 作者报告的探索数据、源码事实和推断。后两者不能替代验收。

主要历史依据：[第三轮报告](../round3-20261021/REPORT.md)、
[正式输入与协议](../round3-20261021/formal/FREEZE.json)、
[历史版本对照](../round2-20261021/HISTORY_TABLE_20261021.md)。

## 2. 剩余成本与收益预算

以下来自第三轮正式批次，用于决定调查顺序；不是当前源码的占比。

| 部分 | 阶段中位数 | 相对总时间的近似占比 | 下一步要拆开的成本 |
| --- | ---: | ---: | --- |
| 加载后查询（前后两次） | 6.511 ms | 39% | 扫描、查找、字符串/blob 访问、数据局部性 |
| 修改 | 3.575 ms | 22% | 高频调用、分配/释放、深复制、搬移、清零 |
| 加载 + 重载 | 2.037 + 3.466 ms | 33% | 输入复制、全图校验、区间登记、空闲表恢复 |
| 独立输出 | 0.714 ms | 4% | 输出分配与复制、稀疏计划、空洞表输出 |
| 完整八阶段总时间 | 16.54 ms | 100% | 包含状态释放等其他阶段 |

阶段中位数之和不一定等于总时间中位数，不能把该表当成精确可加的时间账。
在“其他部分不变”的简化模型中：

- 仅重载耗时减半，对总时间的影响约为 10.5%。
- 加载和重载都减半，对总时间的影响约为 16.6%。
- 修改耗时减少 10%–20%，对总时间的影响约为 2.2%–4.3%。
- 独立输出耗时减半，对总时间的影响约为 2.2%。

这些是 Amdahl 式的算术参照，不是 PR 收益预测；实现可能改变缓存、布局、wire 和
后续阶段的工作量。新基线应使用逐操作原始时间求完整循环，再分析阶段贡献。

历史两项未达标的含义也不同：

- 修改对 cereal 的几何耗时比为 1.053，略慢；联合上界 1.066 未满足 1.05 门槛。
  新修改优化有机会补差，但不能忽略后续安全加固的成本。
- 输出对 Cap'n Proto 的几何耗时比为 0.371，已经约快 2.7 倍，但未达到五倍目标。
  若对方时间不变，XOffset 输出还需减少约 46% 才达到点估计目标；统计过线还需余量。
  这是特定负载的缺口，不是“任何未来格式都不可能达到”的证明。

## 3. 在研优化能覆盖什么

截至 2026-10-22，下表 PR 均未合入参照提交。计时数字来自 PR 作者报告的云端
GCC 16/x86 探索，不是 Mac 正式结果，也不是本次复测。头提交用于识别快照。

| 方向 | PR / 头提交 | 主要覆盖 | 已有探索与剩余边界 |
| --- | --- | --- | --- |
| 8 字节粒度位图 | [#36](https://github.com/ximicpp/XOffsetDatastructure/pull/36) / `a65d500c` | 减少区间索引和临时存储；合并容器头检查 | 仍需完整图遍历、值/顺序检查、输入复制和空闲表恢复 |
| 连续布局游标 | [#38](https://github.com/ximicpp/XOffsetDatastructure/pull/38) / `90ac93c1` | 连续无洞布局避免位图操作，失配后转通用路径 | 包含 #36；普通布局部分重载约降 41%–59%，紧凑布局部分约降 51%–72%；不是整条链路收益 |
| 分配器内联快路径 | [#32](https://github.com/ximicpp/XOffsetDatastructure/pull/32) / `08700f31` | 精确桶复用、无增长尾分配、小块释放，减少通用准备与原子操作 | 尚无可引用的正式计时；拆分、大块、宿主分配和回调仍走通用路径 |
| 保留小桶容量 | [#33](https://github.com/ximicpp/XOffsetDatastructure/pull/33) / `f2a51fb6` | reload/reset 后减少重复桶分配 | 保留容量有空间成本；buffer 销毁、大桶等路径的行为不同，不能泛化成所有加载都无分配 |
| 容器常见路径 | [#30](https://github.com/ximicpp/XOffsetDatastructure/pull/30) / `2d8ed1dd` | append/reserve 的不增长路径、小范围清零 | 实际增长、搬移和深复制仍在；必须确认热路径命中率与代码尺寸效应 |
| 子树段复制 | [#37](https://github.com/ximicpp/XOffsetDatastructure/pull/37) / `2183cabd` | 减少嵌套容器的逐元素分配 | 战斗请求编码 0.446→0.314 ms，应用战斗 0.27→0.24 ms；含适配器变更，需隔离 SHIFT/type opt-in 的贡献 |
| 重载后按需增长 | [#39](https://github.com/ximicpp/XOffsetDatastructure/pull/39) / `236126c4` | 旧使用范围内以 4 KiB 步长重新暴露空间，减少过量清零 | ticks 阶段 0.50→0.38 ms；其他阶段未见收益，不改变所有常规增长行为 |

特别注意：

1. #38 包含 #36，不能相加；T3 单独对一个紧凑 A 输入曾从 360 ns 变为 392 ns，
   T1 再降为 177 ns，说明“所有布局必然受益”不成立。
2. #37 的随机形状测试中，优化路径 `used_end=62904`，参考路径 `19904`，约差 3.2 倍；
   同时 wire 为 8120 对 22312 字节。arena 占用与 wire 必须分别看，不能只报更小 wire。
3. #37 报告的 `B.season_edits` 改善可能来自类型 opt-in 启用 SHIFT，不能全部归因于段复制。
4. 子树复制改变分配次数和布局，会改变其他快路径的命中率。组合必须实测。

## 4. 现有优化之后仍值得研究的空间

### 4.1 加载与空闲表恢复

当前加载在完整校验之后，将空洞逐条恢复到桶和大块 map。位图成本下降后，宿主分配
与元数据恢复可能成为更显著的部分；目前还没有新的占比证明。

候选：按桶计数后一次预留、批量填充、有界元数据复用。保持原分配次序、OOM 和
`new_handler` 重入契约；不能将减少校验当作“恢复优化”。

源码入口：`XBuffer::finish_verified_load`、`XBufferCore::load_free_blocks`
（[生产头](../../../xoffsetdatastructure.hpp)）。

### 4.2 长期碎片与子树复制

大段分配减少调用，但可能难以复用不同尺寸的空洞。需要同时记录命中率、复制/修正字节、
释放方式、尾部增长、宿主空间和下一轮修改成本。

先以存活数据量有界的增删和大小切换负载验证是否稳定，再研究有预算的策略选择、
段大小或显式整理。不得在普通容器修改中暗加会使外部引用失效的隐式搬迁。

### 4.3 查询与数据局部性

当前容器 `data()` 已是简单的相对地址恢复；没有证据表明注册表仍是查询主因。
先拆分标量/样本扫描、记录/属性查找、字符串和 blob 读取，再用采样与机器码验证。

可研究冷热字段布局、批量遍历与显式索引。索引构建、维护、失效、空间和销毁必须计入；
不能使用未来 trace 或缓存预先知道的查询答案。

### 4.4 清零与稀疏输出

M3/M4/M6 解决旧数据与填充泄露，不能直接关闭后参与默认候选排名。可研究的是
有不变量证明的重复写入消除。见 [威胁模型](../../V2_THREAT_MODEL.md)。

当前 `save_verified_into` 已复用单次计算的 gap 列表；跨调用缓存仍是假设。若实现，
必须绑定空闲布局变更版本，覆盖分配、释放、加载、重算、owner 变化和回调边界，
且有释放与空间预算；不得缓存不可信输入的“已验证”状态。

## 5. 下一代架构的研究价值

先研究能力取舍，再决定是否值得产品化；以下均为未实施假设。

| 原型 | 要验证的收益来源 | 必须计入或披露的代价 |
| --- | --- | --- |
| 可变态与紧凑只读 wire 分离 | 去掉输出中的容量/空洞元数据，改善紧凑读取 | 物化、打包、校验与复制；可能不再直接修改接收字节 |
| 分段批次生命周期 | 顺序分配、批次回收，减少逐块管理 | 废弃空间、冻结整理、峰值占用；连续 arena 与元素引用能力变化 |
| 冷热字段分离 | 改善扫描邻接性与向量化 | 随机访问、修改物化、布局维护、生成式访问器及输出成本 |

业界一手资料提供的是机制依据，不是对 XOffset 收益的证明：

- [FlatBuffers C++ Object API](https://flatbuffers.dev/languages/cpp/)：可变对象与紧凑输出分离。
- [Cap'n Proto C++](https://capnproto.org/cxx.html)：顺序 arena 便宜，但丢弃对象会留空间。
- [Protobuf Arena](https://protobuf.dev/reference/cpp/arenas/)：生命周期粒度与跨 arena 复制影响收益。
- [Arrow 格式](https://arrow.apache.org/docs/format/Columnar.html)：扫描局部性与修改成本存在取舍。

新原型使用独立格式标识、规格 oracle 和能力合同。拥有型加载、持有不可变输入的视图、
可变物化、独立输出分别计时；不同模式不能放进同一列宣称全面优胜。

## 6. 后续开发应沿用的实验原则

1. 先补齐源码、工具链、适配器、fixture、真值和运行脚本的可重建闭包。当前正式脚本
   依赖 Mac 外部路径，SLG 的部分设计/适配器未随仓库保存；缺失时该轨保持开放，
   不用地图 demo 替代成绩。旧资料恢复入口见 [归档说明](../../ARCHIVED_EVIDENCE.md)。
2. 区分历史证据 H、当前基线 B0、在研最优组合 B1。每轮冻结实际身份，不跨批次拼倍数。
3. Cold、Pool、Reuse 分别成组。已有 [buffer 复用](../../BUFFER_REUSE.md) 与池化能力
   应被正确使用，但初始化、清理、驻留空间和生命周期差异不能藏到计时外。
4. 先单机制与关键交互，再做整体组合；对子树复制做“库优化 × 适配器/type opt-in”对照。
5. 探索负责选方向，独立确认负责下结论。指标、样本、失败规则和多指标统计在计时前冻结；
   保留无收益、失败和不确定结果，不补样直到通过。
6. 默认采用兼顾完整业务循环与正式基准，受控稳定/峰值内存和 wire 增幅以 10% 为参考
   边界；超预算或改变能力的方案单列为显式模式。具体数值与统计协议须在实验前重新冻结。
7. 内存分开记录虚拟预留、可访问页、宿主容量、池缓存、`used_end` 和 RSS，避免重复记账
   或用进程固定开销稀释增幅。尾延迟须定义操作、负载、采样单位和样本量。
8. Mac 为主验收、原生 Linux 独立复核；WSL、仿真和共享云探索不能冒充原生正式结果。
9. 使用新实验目录，保留不可变档案。完整结构校验、独立输出、清零卫生、别名/回调/OOM
   和跨编译器门禁保持有效；新架构的能力变化单独说明。

建议推进顺序：测量闭包 → 最新基线和下限 → 在研优化归因/组合 → 剩余热点 →
下一代原型 → 独立确认。最终形成可采用的 V2 最小组合，以及下一代架构的取舍报告；
若没有候选达到门槛，保留默认实现也是有效结论。

# 修改阶段时间分析（W9a，2026-10-21）

只做诊断：逐阶段计时（31 轮中位数，stage harness）+ 逐阶段采样剖析（`sample`，只统计当前阶段），没有新的筛选，没有改代码。所有数字是 Apple M4 上的**探索性测量**，用来解释差距，不是正式成绩。正式口径下 W9a 修改 5.09 ms、cereal 3.58 ms（W9 正式批次），对 cereal 上界 1.464。

## 1. 结论

- 对 cereal 的差距约 2.0 ms（stage harness 口径），按成本类别拆：**分配器 +1.5 ms（约 75%）**、**移动所有权协议 +0.56 ms**、**数据写入 +0.62 ms**，cereal 适配器自身代码多 0.5 ms 抵掉一部分。
- **分配器是主因**：XOffset 每次分配或退休约 31 ns，cereal 的 malloc/free 约 15 ns。差别来自 XOffset 的分配器要在 arena 里写 16 字节块头、维护写进 wire 的空闲链表和区间记账、按地址找 owner（macOS 上要经过 TLS 访问）。其中块头和链表属于 V1 格式本身，是结构性的；owner 查找和记账有改进余地。
- **移动协议集中在第 7 阶段（删记录）**：XOffset 每移动一条记录要对 4 个成员做双向所有权检查（防止"把自己移进自己的子对象"），cereal 只是交换指针。这是公开移动语义的要求，结构性。
- **数据写入**：第 4 阶段 `resize(384)` 先把新元素清零，适配器再 `std::copy` 覆盖一遍，同一字节写两次；cereal 是一次 `vector` 赋值。写法由 demo 适配器决定，库内能做的有限（B2 批量初始化探索只省约 1%）。
- **判断**：在 V1 格式、公开移动语义和 demo 适配器都不变的前提下，现有可做的改进（owner 直取、记账、退休路径）估计能省 0.4–0.8 ms，对 cereal 的比值大约到 1.25–1.35，到不了 1.05（推断）。

## 3. 哪些是结构性的，哪些还有余地

| 来源 | 性质 | 说明 |
| --- | --- | --- |
| 每块 16 字节头、空闲链表写在 arena 里 | 结构性（V1 格式） | 改动即改 wire 格式（上一轮的 I1/I2 方向），Q13 已定本轮不做 |
| owner 查找（macOS TLS） | 可改 | B1 owner 直取已实现、门禁通过；两次筛选修改为 0.955 和 0.979，被辅助项规则否决或未过主指标 |
| 区间记账 `note_allocator_block`（第 4 阶段占 37%） | 待查 | 代码本身只有几次比较和写入，占比偏高，可能是采样偏移或对分配器状态行的写依赖；需要指令级确认后才能判断有没有余地（新线索） |
| 退休路径（第 2、3 阶段退休 19%–28%） | 可改一部分 | 退休要查 owner、维护游标；与 B1 有重叠 |
| 原地扩容尝试全部失败 | 可改一部分 | 16,384 次失败的尝试各读一次块头 |
| 双向所有权检查（第 7 阶段） | 结构性（公开移动语义） | 放宽即改变移动的安全保证 |
| 清零后再覆盖（第 4 阶段） | 结构性（demo 适配器写法） | 库内只能让清零更快，B2 探索约 1% |

## 4. 可选方向（交你定）

1. **维持现状**：修改对 cereal 按"不可达"报告，附本分析为证据。

## 1. 结论

1. **正确性：GCC 16.2.0 和 clang-p2996 d77eff1 在 M4 的 Linux arm64 虚拟机上结果完全相同。** 两次运行都是：Release CTest 两边 98/98；S、M 两档规模下，复用和逐条两种口径的四个格式结果一致；两个编译器的逐周期 state 和 wire 字节相同（M 复用第 1 周期 state `acc464551a268253`，与云端 x86-64 相同）；path_audit 正文 1116 行相同；字符串长度分布相同。
2. **Q2（GCC÷clang 墙钟）按冻结规则没有判定。** 允许的两次运行都判为无效（第 3 节），所以 H1 不对 GCC 是落后、持平还是领先下结论。
3. **两次运行的方向一致**，只作参考：A 战斗服往返 GCC 快 3–4%，B 跨服迁移持平，C 分区快照 GCC 快约 30%，D 战报只读 GCC 慢 14–17%。
4. **C 的差距大部分来自 clang 二进制在虚拟机里跑 C 场景偏慢、而且不稳，不是 GCC 真的快 30%。** 同一套 C 场景：原生 macOS 的 clang 是 0.27 ms，稳定；虚拟机里的 clang 是 0.30–0.48 ms；虚拟机里的 GCC 是 0.25 ms，稳定。换成原生 clang 作分母，GCC 只快约 6%。
5. **D 的 GCC 落后不是 XOffset 特有的。** 三家基线自己的 GCC÷clang 在 D 上也是 1.12–1.38。双重比值（xoffset 相对基线，GCC 对 clang）在 D 上是 0.84–1.03（两次运行），说明 GCC 下 xoffset 相对基线没有变差。所以**不开「GCC 16 差距定位」（T4）**。如果以后要查 D.read，建议在云端用 Ir 对比 GCC 和 P2996，云端现在两个编译器都有，比在虚拟机里测墙钟稳。
6. **Q1（xoffset÷基线，GCC 16，M4 虚拟机，复用口径）：A、B、C 对 cereal、FlatBuffers、protobuf 在两次运行里全部 ≤ 0.50。** 最紧的一格是 A÷FlatBuffers：0.469（上界 0.474）和 0.476（上界 0.481）。同一虚拟机里的 clang 在这一格没达标（0.495，上界 0.507；0.503，上界 0.527）。两次运行都无效，这些数字只作参考，不能替代 Mac 原生 clang 的 goal 数据。

## 3. 两次运行为什么无效

| | 第 1 次（队列 015，18:19Z） | 第 2 次（队列 017，19:41Z） |
| --- | --- | --- |
| run.sh | ef7f3eee…2096 | 40ffd8a4…1677 |
| A/A（A*÷A，±1.5%） | A 1.036 [0.71, 1.51] ✗，B ✓，C 1.088 [0.54, 2.17] ✗，D ✓ | A 0.923 [0.41, 2.07] ✗，B 0.972 [0.79, 1.19] ✗，C 0.932 [0.55, 1.58] ✗，D ✓ |
| 漂移（±2%） | 四项都超 | B、C、D 超 |
| 桥接（虚拟机 clang÷原生 clang，> 1.30 判无效） | 没做（原生构建失败） | A 1.050/1.034，B 1.022/0.998，**C 1.415/1.327 ✗**，D 1.140/1.150 |
| vCPU 2 频率（原生 P 核） | 4.03 GHz（4.04） | 4.30–4.37 GHz（4.30） |

原因：
- **单次运行离群**：第 1 次是 A/A 副本的第一次运行，A 慢 12%；第 2 次是第 15 次运行（clang 原件），A 慢 31%。离群运行之前之后的运行都正常，宿主上只有虚拟机进程在忙，频率探针也正常。第 2 次已经改为从虚拟机本地盘运行、每段先预热，离群照样出现，说明是虚拟机本身偶发的变慢。
- **clang 在虚拟机里 C 场景不稳**：`C.snapshot2` 按进程分布在 41–119 µs，GCC 稳定在 17–18 µs，原生 clang 也稳定。C.snapshot 也是虚拟机 clang 48–50 µs，GCC 26–27 µs。
- **桥接超限不是能效核**：频率探针两次都显示 vCPU 2 跑在性能核的频率上。A、B 的桥接比值是 1.00–1.05，只有 C 超过 1.30，D 在 1.14–1.15。脚本里“怀疑能效核”的提示文字在这里不对；按规则批次仍判无效。
- 按设计最多重跑一次，第 2 次之后不再重跑。

# L1 independent source boundary review

Date: 2026-10-19 (Asia/Shanghai). Read-only production-source review; no compilation, native execution, sanitizer run, machine-code inspection or performance measurement performed by this reviewer. No candidate source or request is changed.

Reviewed root C14 `xoffsetdatastructure.hpp` SHA256 `66818de49b18fe85ab8049c9f9ad299bbebbb214eb3fceee0a665fe65f4275c3`; `xoffset_virtual_memory.hpp` SHA256 `90105e4c172da26a5b23cbb10021a18613b458e92b795beee8ec9d7faed72991`. The findings concern L1, independently of M1 v2.

## Decision

**REJECT the proposed context-long canonical origin/address cache. Do not implement it or admit it to S2/S3.** Copy-load is not isolated from reentry, and retaining an OwnerRecord does not retain accessible VM storage.

**Do not admit the alternative that adds owner acquisition and state checking separately to each existing single-recovery helper for ordinary copy-load.** It has no established eliminated expensive work: ordinary `from_bytes` leaves `canonical_byte_origin_` null, and when no direct-receive canonical owner is active the existing recovery starts and ends with one acquire count load. Replacing that with owner acquisition/live-storage/state checks is not a source-level mechanism argument. This is a rejection of that concrete implementation route under the current mechanism gate, not a measured regression or an impossibility theorem for all local designs.

**A smaller local coalescing design is structurally plausible but unproved and not admitted.** The successful path from a container's `checked_relative(data_delta)` through the complete payload/header checks and allocation-header POD copy, ending before range-index insertion, contains no host allocation/free or user callback in the reviewed implementation. It contains a data recovery and a header recovery. A trusted, ephemeral domain proof could potentially recover both addresses within that segment. This does not justify keeping an origin across a whole context, a range insertion, recursion or comparator. No source patch, real-driver optimized opportunity or gain is established here.

## Source evidence and concrete counterexamples

1. **Publication and lifetime.** `init_from_bytes` registers the owner at main-header lines 802–823; `load_verified_with_scratch` constructs the XBuffer before calling graph validation at 5435–5470. `verify_structural_wire_graph` at 4270–4299 constructs two upstream-backed resources and then inserts ranges. Therefore “unpublished return value” does not mean “absent from the owner registry” or “cannot be discovered by a callback.”

2. **Real callback boundary.** `WireValidationContext` at 3904–3918 owns lazy monotonic resources; `register_owned_range` and `register_free_range` at 3945–4002 can call `insert_disjoint`; preparation at 3834–3854 allocates dense/directory/page storage through the PMR resource. The explicit upstream is virtual user code, and its ordinary new/delete resource can reach replaceable allocation/new_handler code. Error construction may also allocate on throwing paths. At minimum the next successful continuation after insertion must not rely on a pre-insertion raw owner/origin proof. `tests/test_validation_v5_bounds.cpp:91` and `tests/test_wire_range_failures.cpp:202` contain real resource/failure boundaries; these existing tests do not claim to execute the retirement counterexample described here.

3. **Retained record, released mapping.** `OwnerRecord` at 641–650 retains a payload number, owner atomic, optional canonical origin and extent; no mapping owner is retained. `unregister_registry` at 849–864 first stores null in `record->owner`, retires its ledger and extracts the registry node. Its comment explicitly states that a cache retains the inert record, never its released mapping. `~XBufferCore` at 323 unregisters; the storage destructor/release at VM-header 234 and 471–493 can cache or unmap the reservation; `release_mapping` at 397–408 clears/unmaps it. Counterexample: scratch callback discovers the registered Core, replaces/destroys its owning object, then returns. A saved `shared_ptr<OwnerRecord>` remains alive while the old mapping is inaccessible. Returning `saved_origin + offset`, or treating a null current owner as “unknown, use ctx.base/raw fallback,” accesses retired storage. This is a source counterexample, not a native reproduction.

4. **Move continuation differs from retirement.** `swap` at 525–541 transfers storage and record together and updates each record's current owner; `move_from` at 825–841 publishes the incoming storage before retired target destruction. A callback can move the reservation into another Core and destroy the original Core while leaving that reservation live. A candidate must reacquire through the retained *record identity*, verify the current owner/storage and required validation state, and continue only if the original address domain remains valid. Dereferencing the original `XBufferCore&` is invalid; blanket rejection solely because the Core object's address changed would also reduce legal move continuation. Existing `tests/test_canonical_cold_no_callback.cpp:175` and `:205` provide owner-move controls in other production paths, not L1 validation coverage.

5. **ABA and state.** A released or pool-cached reservation can later occupy the same numeric payload base. Equality of base/end or a lookup by payload number cannot revive the original record: records are terminal after retirement (639–640, 849–864). Matching an old pointer to a new live record is insufficient. Even a still-live reservation may have changed logical extent or arena/allocator state across a callback; bounds and any needed state/generation must be re-established. Core `m_epoch` is object-associated and swap increments it (538–539), so treating an old Core address plus epoch as the reservation identity does not solve move continuation.

6. **Callback-free recovery itself.** `canonical_bytes_at` at 371–442 performs its acquire count guard, TLS/registry recovery and non-evicting cold lookup. The implementation specifically avoids cache replacement because dropping an evicted terminal record could call replaceable delete. A local proof cannot introduce such eviction/release during its allegedly callback-free segment. Shared_ptr copy is nonallocating; releasing the last inert record is a separate boundary and must be considered.

7. **Actual ordinary path.** VM `from_bytes` at 209–232 copies bytes into the fresh reservation and never starts the explicit canonical byte-array origin; that is set by `for_receive` at 185–205 instead. The main header's canonical guard at 373 returns immediately for zero active canonical owners. An unrelated canonical owner can turn the global cold branch on even though the copy-load target remains ordinary. That case is useful future evidence, but it is not evidence that the fixed ordinary reload driver pays repeated registry resolution today.

8. **User code during traversal.** The reviewed generic `validate_wire_value` at 4176–4212 does not directly dispatch `wire_activation`/`wire_future_lifetime` validation hooks. Avoid claiming otherwise. However set/map checks call `ordered_less`, whose non-string branch invokes `lhs < rhs` at 1857–1863; detail/nonstandard instantiations need an explicit no-user-code proof. More basically the range-index upstream already defeats context-wide reentry assumptions for the public scratch API.

## Unknown fallback versus identified invalidity

Optional provenance unavailable for a public/detail context means run the existing exact helper, preserving its interface domain. The direct `WireValidationContext` construction in `tests/test_validation_v5_bounds.cpp:134` is an example of a legitimate context without an XBuffer owner identity; it must not be rejected just because the optimization cannot prove provenance.

Once an optimization has acquired a specific record, a null current owner, mismatched storage, known retired identity, invalid extent or incompatible generation/state is **known invalidity**, not unknown metadata. Reject safely before reading saved ctx/root/payload addresses. Never fall back to the original raw address after detecting such a condition. Live movement may be continued only after reacquisition and complete required state verification. A new record at the same payload address is not the acquired identity.

## Exact checks and order that a future patch must preserve

`checked_relative` at 4005–4013 performs the delta computation and one-byte bounds validation before canonical address recovery. `validate_binding` retains its zero-delta short circuit. `register_allocation` at 4024–4049 retains, in order: complete payload bounds/alignment; missing-header check; complete header bounds/alignment; header POD read; all offset/size/total/alignment metadata checks; header-inclusive live/free range registration. `register_owned_range`/`register_free_range` retain their owned-before-free overlap priority and their existing null/zero behavior. No recovery optimization may erase these checks, reorder an error ahead of the old first error, or mutate either range index before its existing acceptance point. A copied header value may outlive a callback; a copied payload pointer may not inherit that property.

`register_allocation` itself has one canonical recovery before the header copy; `checked_relative` itself also has one. There is no repeated recovery *inside either helper* to remove by a per-helper owner witness. The two recoveries in the proposed smaller segment are at the container call-site level (`XFixedString` 4114–4118, `XFixedVector` 4142–4146), before the insertion hidden inside `register_allocation`. A correct implementation must make this cut explicit instead of accidentally spanning insertion. Subsequent string terminator access and vector element traversal occur after that potential callback and need fresh lifetime justification.

## Minimum admission proof for a future narrower L1

- Bind an exact immutable source identity and inspect the actual ordinary reload instantiations under the real bare optimized profile. Demonstrate surviving repeated work in the proposed no-callback segment; do not count source calls as cycles or assume an active unrelated canonical owner in the real driver.
- Specify how an ephemeral token establishes the current record identity, current live storage, accessible extent and required validation state. Unknown contexts use unchanged helpers. Identified retirement/replacement never enters raw fallback. Prove storage-aware move/swap continuation and ABA rejection.
- Prove all successful instructions from token creation through final pointer use contain no allocation, deallocation, user comparator or cache-record last release. End/revalidate at every range insertion, resource call and recursion/comparator boundary. Do not infer this from `noexcept` or an unpublished return value.
- Preserve numeric bounds/alignment and header/owned/free first-error ordering above. Include invalid metadata plus simultaneous conflicts, unknown detail contexts, legacy ordinary owners, unrelated canonical owners, canonical one-past/adjacent reservations, scratch move/retirement/replacement and same-address new-record cases.
- Only after a real opportunity exists should validation receive a separate source-bound normal/SAN/codegen request. No timing or screening request is justified by this review.

The current independent L1 route is closed without a production change. This leaves the smaller local design unimplemented and open to a new, separately proved mechanism; it does not block R1/M2 review or M1 validation.

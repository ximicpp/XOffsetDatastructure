# L1, R1, M2: independent mechanism/safety designs

No implementation, integration, benchmark or machine-code conclusion is recorded for these three paths. They do not inherit M1's source or any mechanism admission. Every eventual candidate starts from exact C14. Unknown domain/lifetime facts retain the existing route, without reducing the legal public/detail interface domain.

## L1: local validation address provenance

Current checked_relative computes a numeric target, validates one byte against ctx bounds, then canonical_bytes_at recovers an origin. register_allocation validates complete bytes and alignment, checks that the header exists, canonical-recovers the header address, copies the header POD, validates metadata, then registers the header-inclusive exact owned/free range. WireValidationContext owns two lazy PMR-backed indexes; range insertions may allocate. validate_wire_value may invoke custom validation. verify_structural_wire_graph begins with an already registered owner and constructs this context; it does not isolate the mapping from callbacks.

Therefore a context-long canonical origin/payload pointer is unsafe without a separate storage-lifetime contract. OwnerRecordPtr retains a record, not its VM mapping. A scratch upstream/new_handler can move, replace or retire an owner. Moving a Core may preserve mapping but replacement need not, and generation changes cannot be hidden by numeric range equality. An active canonical owner elsewhere can also change the global fast path without altering this ctx's payload. These cases require actual per-domain proofs, not a blanket 'unpublished' flag.

A possible safe unit is one no-allocation/no-deallocation/no-user-code helper segment: re-resolve the current owner from a trusted identity, check its live owner/storage/state/generation and that ctx bounds still name that storage, recover a canonical byte origin when appropriate, validate the original numeric target/range/alignment in its original order, use the recovered address, and end the local proof before index insertion or custom recursion. A header POD copied within this segment can survive a later callback as a value, but a payload pointer cannot. Unknown public/detail contexts must keep the original helper exactly. Re-resolving separately at every helper may exceed the original count-load/branch cost for ordinary copy-load; that is a concrete mechanism rejection possibility.

Before code exists, establish whether any repeated canonical recoveries occur inside such a segment in the actual reload driver. If all useful pairs are separated by index allocation/custom dispatch, or local proof adds owner lookup to the original zero-active fast path, do not implement a context-wide cache. No committed L1 patch yet; source safety cannot be closed by deleting callbacks or changing validation order. Required future counterexamples include canonical unrelated owner, legacy/noncanonical domain, scratch callback Core move/replacement/retirement, invalid header alignment/range, simultaneous owned/free overlap with original owned-first error, and unknown detail callers.

## R1: inactive canonical hot/cold split

canonical_bytes_at already starts with canonical_active_count_.load(acquire)==0 then nullptr. The cold body has TLS/cache access, containing-anchor priority (including zero-length one-past), target fits, owner liveness, canonical-origin recovery and registry cold lookup. The actual read driver must first show that inlining/outlining still leaves an avoidable call or cold body footprint. If its hot path is already load/test/branch, no new candidate is justified by source size alone.

A prospective change is only an out-of-line private cold helper entered after the existing acquire load observes nonzero. It must retain all TLS shutdown availability rules, cache ordering, nonallocating/reentrant replacement handling, anchor-first adjacent-reservation semantics and target bounds. It adds no persistent negative cache and never hoists the load across calls. Normal/SAN must retain canonical_zero_target, canonical_cold_no_callback and canonical_registry_v2 counterexamples, callback/new-handler replacement, move/release/reuse and one-past checks. No R1 source is written while optimized opportunity remains unknown.

## M2: data reuse inside one exact owns traversal

move_assignment_owns_address recursively checks actual inline storage plus dynamic allocation reachability. The bidirectional owning containment checks at assignment sites must remain. Only a parsed data pointer/count held within one invocation and a demonstrably callback-free traversal segment could be reused. It cannot become a cross-operation locator or persistent arena cache; same-arena and numeric order never establish absence of ancestor/descendant ownership.

First inspect actual ordinary Record/Attr owning recursion to see whether data() resolution survives optimization more than once per vector node. If the compiler already reuses it, reject the mechanism. A source change could name a local pointer for range check and loop only when no intervening call can allocate, free, invoke custom code or invalidate storage; unknown subtrees keep the old recursion. Re-evaluating bidirectional ancestors, different elements, nested owning children, legal independently located descriptors, VM owner movement/retirement/reuse and callback cases remains mandatory. No M2 source is written yet, and closed transparent locator/cursor/allocation/bitmap mechanisms are not reopened.

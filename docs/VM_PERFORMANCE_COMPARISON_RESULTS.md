# XBuffer 虚拟内存存储性能对比（macOS arm64）

实测结论：当前改造的主要收益是避免增长与首次保存时的整块 arena 搬迁，降低大缓冲区的总耗时及单次增长停顿。预分配后追加速度基本相同；大量小缓冲区和 64 MiB 加载出现回退。不能据此宣称所有操作都加速。

正式实验时间：2026-10-13 10:04–10:05（Asia/Shanghai）。只使用修正输入读取后的完整重跑结果。源码、测量程序和结果均保留在本地 `next_cpp26` 工作区，未提交或推送。

## 对照与方法

- 旧版：固定提交 `07d649909d7f43ca0d11b85accb6d9dab991e284` 的 vector 实现；新版：当前工作区冻结快照。分支 `next_cpp26`，HEAD 仍为相同旧版提交。
- Apple M3 Pro，12 核，36 GiB RAM，macOS 26.6.2 arm64，16 KiB 页；接入交流电，开始与结束时 swap 使用均为 0。
- 同一 Bloomberg P2996 Clang 21、SDK 26.5、`-O3 -DNDEBUG -std=c++26 -freflection -fexpansion-statements -stdlib=libc++`。两版保留 reflection、类型/schema/graph 验证；不使用禁用验证的性能分支。完整编译参数见 metadata。
- Boost、typelayout 两侧相同且干净，分别为 `da041154c6bac1a4aa98254a7d6819059e8ac0b0`、`9a6de1d73617631a9612ba9f572d6c0844a90b19`。
- 18 组负载；每组每版 1 次预热、7 次正式运行。共 252 个正式样本、36 个预热样本。每个样本是独立进程，每对交替旧版先运行／新版先运行；测量串行执行，期间没有测试或编译并行运行。
- 时间只取程序内部 `steady_clock` 计时区间，排除进程启动、输入文件读取、准备数据和完整内容校验。增长/追加的总时间包含少量相同的采样与计数开销；单次 grow 计时只包围 grow 调用。
- grow 从 4 KiB 起，每次增加至多 4 MiB。旧默认预留 64 KiB，VM 显式上限设为目标大小；128 MiB 案例并非 VM 默认配置。同预留组两版从开始就预留完整目标范围。
- 追加 `uint32_t`，缓存 root，仅在 `XBadAlloc → grow → 重取 root` 后重试。两版用相同显式算法；并未测量自动增长。预分配组在计时前准备足够逻辑空间和相同初始预留预算。
- 多缓冲区均从 4 KiB 逻辑长度起，先全部创建，再按最老优先顺序逐个分配 16 个 `uint64_t`，最后释放并销毁。总耗时包含这四个阶段。
- save/load 使用 `VmBenchRoot { uint64_t marker; XVector<uint32_t> values; }` 和稳定 schema 名称。首次 save 每次使用新对象；准备逻辑空间为 `2 × payload + 1 MiB`，两版在计时前均写过整个范围。循环组执行 8 次 save 后 grow 回准备长度，只累加 save/grow 区间。
- load 使用由两版分别生成、逐字节比对一致的外部 fixture；输入 string 按文件长度一次分配后完整读取并保持存活。两版输入和加载容量均相同，包含完整 verified 校验。
- 每个样本在计时外逐项核对全部 payload；两侧 checksum、wire 长度、失败重试数、增长次数、操作数、最终逻辑长度一致。所有 VM 测量样本在操作期间均未改变 base。

当前工作区还包含注册表同步、实际地址对齐和 handle／类型安全修复。因此这里是两个完整实现的对照，不是只切换 mmap 的单变量消融实验。尤其不能把多缓冲区回退全部归因于某个系统调用。

## 增长停顿与地址稳定

下面的停顿为每次 grow 调用时长。每格给出「各 trial 最大值的中位数 / 全部 7 个 trial 中最大值」。增长只有 16／32 次，p99 等于最大观测值，不能解释成生产环境 p99 保证。追加批次计时单位是至多 4096 个元素，多缓冲区批次是 16 次分配，两者不是单元素延迟。

| 负载 | 旧停顿中位 / 最大 ms | VM 停顿中位 / 最大 ms | 旧 base 变化 / VM | 旧额外 arena 搬迁量估计 MiB |
|---|---:|---:|---:|---:|
| 小起点增长：旧默认 / VM 目标上限 64 MiB | 1.855 / 1.954 | 0.187 / 0.193 | 5 / 0 | 60.020 |
| 小起点增长：旧默认 / VM 目标上限 128 MiB | 3.690 / 4.216 | 0.207 / 0.212 | 6 / 0 | 124.023 |
| 小起点增长：相同预留 128 MiB | 0.238 / 0.277 | 0.198 / 0.225 | 0 / 0 | 0.000 |
| 追加：显式增长重试 1,000,000 元素 | 0.841 / 0.869 | 0.338 / 0.388 | 8 / 0 | 15.938 |
| 追加：显式增长重试 10,000,000 元素 | 13.895 / 14.567 | 5.608 / 5.811 | 12 / 0 | 255.938 |
| 保存后再增长 × 8 64 MiB | 1.841 / 1.925 | 0.475 / 0.494 | 16 / 0 | 1024.003 |

128 MiB 默认旧策略增长的最大单次停顿，中位值从 3.690 ms 降到 0.207 ms；同等完整预留时，两版原本都不会搬迁，提升较小。64 MiB 首次 save 的旧版每个样本移动一次 arena，新版均为零次；8 轮 save/grow 的旧版为 16 次，新版为零次。

`relocation_copy_bytes_est` 只按地址变化时的旧逻辑长度推导额外 arena 搬迁量，首次 save 的搬迁按收缩后长度推导；不含容器迁移、wire string 复制，也不是硬件带宽或系统追踪实测。`zeroed_new_bytes` 只统计显式 grow 新暴露逻辑范围，排除构造/load；两版 grow 都主动写零。`vm_enable_calls_est` 只统计 grow 导致可访问页范围增加的次数，未单独测量 mprotect 耗时，也不统计构造时的启用。

## 内存与地址空间

RSS 是操作完成且对象仍存活时的**整个进程**驻留量，含 string、分配器缓存等；不是 arena 独占物理页数。Mach `TASK_VM_INFO` 以字节记录，CSV 转成 MiB。旧 vector 当前容量、VM 硬上限、可访问页范围、RSS 分别记录；峰值是采样时截至当时的进程历史峰值，含准备阶段，不能当作计时阶段净峰值。`memory_peak` 在计时后、额外内容校验前采样，`memory_after_validation` 另含校验结束时的历史峰值。

| 场景 | 最终逻辑长度 MiB（两版相同） | 旧当前容量 / VM 硬上限 MiB | RSS 旧 / VM MiB |
|---|---:|---:|---:|
| 小起点增长：旧默认 / VM 目标上限 128 MiB | 128.000 | 128.125 / 128.000 | 254.17 / 129.95 |
| 小起点增长：相同预留 128 MiB | 128.000 | 128.000 / 128.000 | 129.98 / 129.95 |
| 追加：显式增长重试 10,000,000 元素 | 256.000 | 256.000 / 256.000 | 514.22 / 258.12 |
| 追加：预先分配足够逻辑空间 10,000,000 元素 | 129.000 | 256.000 / 256.000 | 260.03 / 131.00 |
| 首次 verified 保存 64 MiB | 64.000 | 64.000 / 129.000 | 323.08 / 259.03 |
| verified 加载 64 MiB | 64.000 | 64.000 / 64.000 | 130.09 / 130.08 |
| 保存后再增长 × 8 64 MiB | 129.000 | 129.000 / 129.000 | 387.12 / 323.08 |

本机大缓冲区完整生命周期 RSS 有明显下降，与减少 malloc 搬迁后保留的旧内存块相符。不能解释成 vector 的预留容量全部物理驻留，也不保证换 OS/分配器后仍有同样比例。千万次追加的有效 payload 约 38.15 MiB，但逻辑 arena 增长到 256 MiB：容器扩容的旧块、自由表及显式翻倍策略仍有空间放大，VM 并未解决这些问题。

首次保存 64 MiB payload 后，VM 逻辑长度约 64 MiB，但仍保留 129 MiB 可访问范围及预留区。它没有把尾页归还系统；这里观察到的进程 RSS 较低不构成 decommit 已实现的证据。

|---|---:|---:|---:|---:|---:|
| 多缓冲区：各自默认 1,000 个 | 0.0625 / 64.0000 | 0.061 / 62.500 | 0.000 / 62.500 | 415.135 / 477.635 | 18.12 / 17.89 |

5000 个默认 VM arena 共预留 312.5 GiB 地址空间，RSS 约 81.44 MiB；改成每个 64 KiB 上限后，地址预留总和只有约 0.305 GiB。旧列表示可越过的 vector 当前容量／初始预留提示，新列才是 VM 硬上限。旧版 OS 地址增量接近零，与使用 malloc 已有的大型虚拟区域相符，并不表示旧版不占地址空间。默认 64 MiB 上限不适合海量 4 KiB arena。

## 回退分析与下一步

5000 个默认小缓冲区：

| 阶段 | 旧 ms（中位数） | VM ms（中位数） |
|---|---:|---:|
| 创建 | 69.331 | 75.707 |
| 分配 | 252.165 | 362.608 |
| 释放 | 247.405 | 358.976 |
| 销毁 | 0.447 | 9.601 |

各阶段单独取中位数，四列之和不必等于总耗时中位数。两版仍遍历全局 owner 链表；新版增加同步与元数据，另有映射创建/销毁成本。本组把这些成本共同测出来，尚未拆分锁、缓存命中与系统调用各自贡献。即使两版初始预留均为 64 KiB，5000 个缓冲区仍从 569.52 ms 增至 740.45 ms，缩小预留量本身没有消除查找开销。

64 MiB verified load 从 3.547 ms 增至 4.112 ms，两版操作后 RSS 几乎相同，约 130.1 MiB。源码显示旧版从字节范围直接 assign；VM 构造先对整个逻辑范围 memset，再 memcpy 输入。这是额外写入的潜在原因，当前实验没有把它与验证、映射/页错误成本分别计时。

基于本次结果，后续优化优先级：

1. 为从字节构造/load 提供可靠的直接写入路径，避免新映射先清零再覆盖；保持原有失败和验证语义。
2. 改进 owner 查找以及小 arena 的映射创建/回收成本，并为海量小对象使用显式较小上限。
3. 改进容器尾部原地扩展和自由块管理，降低追加时的逻辑空间放大。
4. 若需要真正降低 save 后物理页占用，单独实现并测量尾部 decommit；若需要减少 wire 复制，单独设计分段输出。

本次仅新增实验程序与结果文档，没有根据这些建议继续改动生产实现。

## 审计、限制与复现

首轮使用 `istreambuf_iterator` 读取 fixture，string 扩容会释放大块内存；旧 load 随后可能复用驻留页。修正为一次分配读取后，重新跑完全部 18 组；首轮所有耗时均排除于正式汇总，未选择更快的样本混合。原始首轮保存在 `build/perf_vm/20261013_native_7pairs` 供检查。

只有本机 macOS 原生性能结果；此前 Linux/Windows 的正确性覆盖不等于性能验证。没有 CPU 绑核、固定频率、硬件事件追踪或生产并发负载；桌面后台活动仍可能影响结果，特别是多缓冲区长链访问。7 对样本提供局部稳定性证据，不能外推完整延迟分布。

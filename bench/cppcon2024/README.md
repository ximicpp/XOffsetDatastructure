# The CppCon 2024 comparison, re-run with 4.0

The CppCon 2024 talk (tag `v1.0.0`, `benchmark/xbenchmark3.cpp`, results in section 3 of the README of
the time) compared 8 libraries on one game character, `Character`: send+receive time, read/write loop
time and message size. This directory redoes the same comparison with the 4.0.0 library: the data
shape, the read/write loop and the rivals are the same as in 2024, and the measurement rules are
today's.

## How to run

```sh
bench/cppcon2024/run.sh <output directory>          # RUNS=7 CPU=2 adjustable; QUICK=1 for a smoke run
```

Needs git, python3 and docker (building the image the first time needs network access). The script
builds the toolchain image (`Dockerfile`: the same GCC 16.2 image as the 4.0 scorecard, plus Debian 13's
protobuf 3.21.12, Cap'n Proto 1.1.0, FlatBuffers 23.5.26, msgpack-cxx 7.0.0 and zstd 1.5.7), fetches
zpp_bits v4.7.6 and cista v0.16 on the host at the commits pinned by the scorecard, generates code for
the three IDLs (`schema/` holds the 2024 `.proto`, `.fbs` and `.capnp` unchanged), compiles with
`-std=c++26 -freflection -O3 -DNDEBUG`, runs `RUNS` processes pinned with `--cpuset-cpus`, and
`summarize.py` takes the median of each item and puts it next to the 2024 number.

Compiling with `-DCC24_PARTS=1` (equipment), `2` (path points and attributes) or `4` (items) runs only
part of the read/write loop, to see where the time goes.

## Scenario and rules

- Data: the same shape as 2024: 64 items (a map), 16 path points, 16 attributes, 8 pieces of equipment
  with 8 attributes each, 4 skills, an 8-byte name.
- Read/write loop (per iteration): +1 on 4 scalars, change the position, 4 times (append a piece of
  equipment with 8 attributes, then remove it), append 8 path points and 1 attribute, insert and erase an
  item, remove those 8 points and 1 attribute, −1 on 4 scalars. In 2024 each timed iteration drew 85
  `mt19937_64` random numbers, which cost about as much as the data operations themselves; here the
  random numbers are generated before timing, and timing covers only data reads and writes.
- Everything removed is really freed by every library (since 2026-11-17). Protocol Buffers removes
  equipment and path points with `DeleteSubrange`, which deletes the removed messages, just as the other
  libraries really allocate and free every iteration. Its default `RemoveLast` keeps the cleared message
  in the repeated field and the next `add_` reuses it, so the whole loop never allocates; that style is
  listed on a separate report-only row (`Protocol Buffers reuse`).
- The item key is different on every iteration (since 2026-11-17): before timing, 100,000 splitmix64
  values are generated by iteration number and read in order, the same for every library. Other values
  still come from a 1024-entry ring. Previously the keys also came from the ring, so each key repeated
  about 100 times per round, and the 1024 paths of the branchy binary search (`std::lower_bound`) in std
  and cista were memorized by the branch predictor, which the branchless lookup of XOffset's `XMap` does
  not benefit from; running only the items part, the cista raw tuned style went from 28 ns to 53 ns and
  XOffset from 41 ns to 49 ns.
- Send = in-memory state → bytes another process can use; receive = bytes → state the receiver can read
  and modify (the 2024 wording).
  - XOffset: `save_verified_into` / `save_verified`; receiving uses the trusted tier
    `XReceiver<XLink::server_peer>` (`reload` into a reused buffer / `load` a new one). The full
    validation tier (`reload_verified` / `load`) is report only.
    The scored rows send a buffer that was filled once. `sr_reuse_after_rw` (report only) sends the
    buffer the read/write loop has run on, whose wire also carries spare capacity and freed blocks.
  - zpp::bits, MessagePack: encode std objects, decode into std objects.
  - Protocol Buffers: as in 2024, the state is the mutable protobuf message: `SerializeToString` +
    `ParseFromString`.
  - FlatBuffers, Cap'n Proto: build the message from std objects, and the receiver reads it out into std
    objects (messages in these two formats cannot grow or shrink in place, so modifying means unpacking,
    the argument of section 1.2 of the 2024 README). FlatBuffers does not run the Verifier; read-only
    access (no unpacking) is a separate report-only row. Cap'n Proto's reads carry bounds checks that
    cannot be turned off.
  - cista raw / offset: as with cista in the 4.0 scorecard, the receiver copies the wire into its own
    buffer and deserializes in place (raw with `mode::UNCHECKED`, offset with `mode::CAST`, neither
    validates), and the object stays in the buffer where it can be modified.
- Two send+receive modes: reuse (both ends reuse buffers and objects, the normal case in a server loop)
  and fresh (new for every message, the 2024 style).
- The item map uses the same kind of container in every library: the std model and cista both use a
  vector sorted by key (flat, like XOffset's `XMap`), and insert and erase run the same code
  (`items_upsert` / `items_erase_at` in `common.hpp`). In 2024 the std rival used `std::map` and cista
  `hash_map`; the former was made flat in the 2026-11-03 fairness review, and the latter was dropped in
  this version, so a hash map is no longer compared with an ordered map. Protocol Buffers uses the 2024
  `.proto` unchanged, with items as its `map<>` field.
- Each format's decoded state is compared field by field with the sent state once (not timed), and the
  state after the read/write loop is compared with the std model.
- Bytes: raw size and zstd level 3 (compression is not timed). The wire format is not adjusted to shrink
  bytes; bytes are report only.
- Two sets of read/write rows. "2024 layout": the 2024 data layout and element-by-element style
  (`rw_once`), the same for every library. "Tuned style": equipment attributes stored inline when there
  are at most 8 (longer ones go into an overflow vector), the 8 path points appended at once and removed
  at once, and items erased by the position returned from insert (`rw_tuned`; for XOffset
  `rw_xoffset_bulk`). Tuning is applied to every model that can be written this way: XOffset
  (`xoffset inline`), the std model (`std inline`, also the state of `zpp::bits inline`), cista
  (`cista raw inline`, `cista offset inline`). Protocol Buffers messages have no inline scalar arrays,
  `RemoveLast` keeps cleared objects anyway (the scored row uses `DeleteSubrange` to really free, see
  above), and the only usable bulk call is adding attributes as a range (`Protocol Buffers bulk`). The
  schemas of FlatBuffers and Cap'n Proto are fixed by their IDLs, and their reads and writes use the std
  model.
- Both sets of XOffset read/write rows use one `edit()` per iteration. One `edit()` around all
  iterations of a round is report only (`rw_one_scope`).

### Send + receive of a modified buffer

The scored rows send a buffer that was filled once: XOffset's best case, since its wire is the buffer and
carries spare capacity and freed blocks. The report-only rows `sr_reuse_after_rw` send the buffer the
read/write loop has just run on (same state, after heavy churn). A separate run of 15 processes
(library 6efd9e24, [`results/2026-11-17-modified-buffer/summary.md`](results/2026-11-17-modified-buffer/summary.md)):

| XOffset, 2024 layout | Wire bytes | zstd-3 | ns | ÷ zpp::bits | ÷ cista raw |
| --- | ---: | ---: | ---: | ---: | ---: |
| Trusted tier, as filled | 3,064 | 2,986 | 78 | 0.25 | 0.12 |
| Trusted tier, after the read/write loop | 7,928 | 3,173 | 181 | 0.57 | 0.27 |
| Full validation tier, as filled | 3,064 | 2,986 | 191 | 0.60 | 0.28 |
| Full validation tier, after the read/write loop | 7,928 | 3,173 | 331 | 1.04 | 0.49 |

- On the trusted tier a modified buffer is still faster than zpp::bits in all 15 processes; on the full
  validation tier it ties.
- One read/write iteration plus one send + receive of the modified buffer: 331 ns (2024 layout) and
  250 ns (tuned), 0.51 and 0.63 of zpp::bits on std containers, 0.36–0.37 of cista.
- `save_compact` writes the state without spare capacity and free blocks in 3,552 bytes; it walks the
  state, so it is not free.
- In this run the tuned read/write loop against cista raw was 0.98 (faster in 9 of 15 processes): read
  that margin as a tie to a small win.

### Realistic RPG character & iso-byte structural complexity (`complexity_bench.cpp`)

The original 2024 `Character` is unusually flat: ~80% of its 2,916 `zpp::bits` bytes live in four
flat vectors of fixed-size POD records (`items`, `path`, `attributes`, `skills`), there are only
14 dynamic containers/strings in total (`name` is an 8-byte SSO string), and the schema has depth 2.
Replaying an identical flat object into reused containers lets `zpp::bits`, FlatBuffers (inline
`struct` arrays), and cista approximate bulk `memcpy` with zero heap allocations.

`complexity_bench.cpp` (`bench/cppcon2024/run_complexity.sh <out-dir>`) benchmarks all 8 original
libraries on both the 2024 flat shape and a realistic depth-4 RPG `RichCharacter`
(`schema/rich_character.{fbs,capnp,proto}`: >SSO strings everywhere, items with name + affixes +
flags, equips with name + creator + attributes + gems + bonuses, skills with name + effects + tags,
quests with title + objectives + descriptions), verified field-by-field before timing and smoke-checked
under ASan + UBSan + LSan:

- **2x2 iso-byte control**: `Flat-3KB` (14 containers) vs `Rich-3KB` (107 containers, depth 4) both
  stay inside a 32 KiB L1d cache; `Flat-12KB` (38 containers) vs `Rich-12KB` (373 containers, depth 4)
  match commercial RPG character state.
- **Realistic server scenarios**: 16-shape `varied_reuse` (fits in L2 so `std` decoders cannot skip
  container reallocations), `fresh_trusted` and equal-check `fresh_checked` (new wire + new live
  session object per player), `hop_trusted` and `hop_checked` (`Receive -> Gameplay Mutate -> Send`
  over 16 varied players: update scalars/pos, >SSO title/quest desc, equip/gem, loot a new `RichItem`
  with affixes/flags, erase an item), in-place gameplay tick `rw_rich`, and read-only zero-copy
  `view_admit` / `view_bounds`.

Cloud Intel Xeon Skylake @ 2.19 GHz (32 KiB L1d, GCC 16.2 `-std=c++26 -freflection -O3 -DNDEBUG`,
pinned to CPU 2, 9 independent processes with randomized library order, medians; full tables:
[`results/2026-11-26-realistic/summary.md`](results/2026-11-26-realistic/summary.md) and refreshed
classic 2024 run [`results/2026-11-26-realistic/classic_summary.md`](results/2026-11-26-realistic/classic_summary.md)):

## The 2024 demo

The other 2024 demo (`demo/xdemo.cpp`: one platform writes `data.bin`, another reads it and keeps
modifying it) corresponds in 4.0 to `examples/demo.cpp`, `examples/helloworld.cpp` and the cross-device
mesh demo. This directory's `character_demo.cpp` writes, modifies and reads back the same Character
(compiling needs only the library headers, C++20):

```sh
c++ -std=c++20 -O2 -I. bench/cppcon2024/character_demo.cpp -o character_demo
checksum=$(./character_demo write character.xwire)
./character_demo modify character.xwire character.changed.xwire "$checksum"
./character_demo verify character.changed.xwire
```

The modifying process can run on another platform. The read-back process runs on the platform that
wrote first and checks the complete state against an independently generated reference object.

# X4 同机进程间交接（memfd 封印）：云端结果

2026-10-22 · 「可修改可重定位定位」线程 · 分支 `claude/mutable-relocatable-positioning`

**口径**：云端 Firecracker 虚拟机（Intel Xeon 2.10 GHz，4 核，Linux 6.18.44），官方 `gcc:16` 镜像（GCC 16.2.0，`-std=c++26 -freflection -O3 -DNDEBUG`），绑在 2、3 号核上。子进程是 fork 出来的另一个进程，两边用 Unix socket 通信。每格是 100 次往返的中位数（第一次往返子进程还要算整份摘要，不计时），减去 1 字节往返（"ack"）。两轮（`out_x4_run1.txt`、`out_x4_run2.txt`），写成"第 1 轮 / 第 2 轮"。**这台机器只能看比例和量级**；P2996 Clang 一侧没测。

程序：`handoff.cpp`；构建和运行：`build_handoff.sh`。状态用 `bench/slg` 的模型：玩家（payload 11.5 KB）、M 规模地图分片（890 KB）、L 规模地图分片（3.55 MB），都先改过，arena 里有空洞。

## 1. 原型做了什么

库头文件里加了四个接口，只在本分支、只在 Linux：

| 接口 | 做什么 | 复制 |
| --- | --- | --- |
| `save_sealed<T>()` | 把 payload 写进一个新的 memfd，封印（禁止写、缩、扩），返回描述符；源 buffer 不变，可以接着改 | 发送方一次 |
| `create_shared<T>(n, cap)` | 新建 buffer，arena 从一开始就是一个 memfd 的共享映射 | 无 |
| `release_sealed<T>()` | 把这样的 arena 整块交出去：本进程解除映射（buffer 变空，和移动之后一样），在 payload 两边写上头部页和空洞表，截到最终大小，封印，返回描述符 | 无 |
| `load_verified_sealed<T>(fd, cap)` | 先查封印（必须禁止写和缩），按 `load_verified` 的规则检查头部，把 payload 页写时复制地映射进来，原地跑同样的完整结构校验 | 无 |

文件格式（原型）：偏移 0 是 V2 wire 头，payload 从第二页开始（稠密），空洞表在 payload 之后按页对齐的位置。

封印让"校验完以后字节不会再变"成立：`F_SEAL_WRITE` 只有在没有任何可写共享映射时才加得上，加上之后谁也不能再写这个文件；`F_SEAL_SHRINK` 保证文件不会被截短，映射不会触发 SIGBUS。所以接收方可以原地校验、原地使用，不用先复制一份（可重定位本质里的 O7 独占要求）。只有 `F_SEAL_FUTURE_WRITE` 不够：它不管已经存在的可写映射。

接收方映射用的是 `MAP_PRIVATE`：改动只复制被改到的页，永远不会写回文件。空间不够时照常在后面的匿名页里增长。

## 2. 结果

### 2.1 一次交接（父进程发，子进程收下并只碰一下根，再回 1 字节），µs

| 路径 | 玩家 11.5 KB | 分片 M 890 KB | 分片 L 3.55 MB |
| --- | ---: | ---: | ---: |
| stream：`save_verified` + write，read + `load_verified` | 49 / 41 | 1,329 / 1,025 | 4,015 / 5,124 |
| fd+copy：同样的 wire 放进封印 memfd，mmap + `load_verified` | 72 / 65 | 1,443 / 1,275 | 4,976 / 5,261 |
| adopt：`save_sealed`，`load_verified_sealed` | 43 / 62 | 961 / 739 | 3,012 / 2,805 |
| move：`release_sealed`，`load_verified_sealed` | 46 / 68 | 651 / 566 | 1,645 / 2,024 |
| move ÷ stream | 0.94 / 1.68 | **0.49 / 0.55** | **0.41 / 0.39** |

### 2.2 子进程收下后接着改（玩家 16 次赛季编辑，分片 1 个 tick），µs

| 路径 | 玩家 | 分片 M | 分片 L |
| --- | ---: | ---: | ---: |
| stream | 46 / 38 | 947 / 1,046 | 3,660 / 5,332 |
| adopt | 73 / 76 | 1,409 / 1,411 | 4,913 / 5,193 |
| move | 81 / 83 | 1,292 / 1,210 | 3,966 / 5,231 |
| move ÷ stream | 1.77 / 2.17 | 1.36 / 1.16 | 1.08 / 0.98 |

### 2.3 拆开看（同一进程里，µs）

| 步骤 | 玩家 | 分片 M | 分片 L |
| --- | ---: | ---: | ---: |
| 发送 `save_verified`（复制到 `std::string`） | 0.16 | 36 | 311 |
| 发送 `save_sealed`（复制进 memfd，含 close） | 8.1 | 196 | 939 |
| 发送 `release_sealed`（不复制，含 close） | 11.9 | 33 | 104 |
| 接收 `load_verified`（从内存） | 17.8 | 530 | 2,192 |
| 接收 `load_verified_sealed`（同一个 fd） | 16.9 | 201 | 872 |

（取第 1 轮，第 2 轮相差在 11% 以内。）

## 3. 结论

1. **原地校验省掉了接收方的大头。** 1 MB 以上的状态，`load_verified_sealed` 是 `load_verified` 的 0.38–0.41 倍：不复制，也不用给新的匿名页清零，剩下的基本就是校验本身。
2. **从一开始就放在共享 memfd 里，整块交给另一个进程，两边都不复制。** 接收方只读或少量修改时，一次交接是 socket 流式的 0.39–0.55 倍（890 KB、3.55 MB）。这是"把一个活的数据结构移动到另一个进程"：同一份字节，换了地址、换了进程，不经过编码、解码或复制。
3. **写时复制会把收益吃回去。** 接收方改动遍布整个 payload 时（分片 tick 几乎碰到每一页），每页一次缺页加 4 KB 复制，adopt 变成 stream 的 0.97–1.49 倍，move 是 0.98–1.36 倍。玩家这么小的状态，memfd 和映射的固定开销（十几 µs）比复制还贵，stream 更快。分界在 11.5 KB 和 890 KB 之间，没有细测。
4. **把 wire 放进 memfd、接收方再复制（fd+copy）没有意义**：每种大小都比 stream 慢。`save_sealed` 的复制本身也比复制到 `std::string` 慢 3–5 倍（分片；往 shmem 写要逐页分配），所以 adopt 不如 move。
5. **可以做成策略**：发送方大状态用共享 arena + `release_sealed`；接收方预计只读或改得少就 adopt，要大面积改就 `load_verified` 复制一份。

## 4. 正确性（两轮都通过，共 66 项）

- 收下的内容、空闲表和源一致，再保存出的 wire 和源逐字节相同。
- 收下后改动只在本进程：同一个文件再收一次，内容还是原来的。
- 收下后接着改，超出文件页的部分照常增长，再按 `load_verified` 往返一致。
- `release_sealed` 之后发送方 buffer 为空，文件带着封印。
- 拒绝：没封印的 memfd、只封了"禁止缩"的 memfd、schema 指纹不对、文件大小和头部对不上。
- 差分：根对象前 8 个 8 字节字各自写坏，封印路径和 `load_verified` 对同样的字节给出相同结论（各拒绝 5 个；另外 3 个是标量字段，两边都接受，这正是"不保证内容完整性"）。

## 5. 还没做的

- 没有 fuzz 封印路径；没测 hugetlb memfd、cgroup 记账（shmem 页在写时复制之前记在发送方）。
- `release_sealed` 写头部或封印失败时，buffer 已经交出去了（原型直接丢弃）。
- `MAP_FIXED` 映射失败时，预留区里会留下一个洞；正式实现要先映射再替换，或者用 `MAP_FIXED_NOREPLACE`。
- 共享 arena 不回收尾页（`MADV_DONTNEED` 对共享文件页不清零），也不进 `XBufferPool`。
- 只有 Linux。macOS 没有 memfd 和封印，同等语义要用 Mach 内存对象，另做。
- 没有在 Mac 上测；要对外引用，按 `PERF_GOAL.md` 的口径排队。
